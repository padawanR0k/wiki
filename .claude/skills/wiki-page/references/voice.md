# r0k Wiki 말투 레퍼런스

이 파일은 `content/` 안의 실제 글에서 추출한 문체 규칙이다.
"간결하게", "실용적으로" 같은 형용사 지시로는 이 말투가 재현되지 않는다.
아래 규칙과 발췌를 그대로 따르는 것이 목표다.

---

## 0. 절대 원칙

**AI가 쓴 티가 나는 순간 실패다.** 아래는 이 위키에 단 한 번도 등장하지 않는 것들이다.

- "~할 수 있습니다", "~하시기 바랍니다" 같은 안내문체

  경어체는 소수 문서에만 있다. `monitoring/datadog RUM.md`가 13회로 사실상 유일한 경어체 글이고, `seo/nextjs dynamic sitemap.md`(6회, draft), `web/video player.md`(2회), `tip/키보드 안쓰기.md`·`tip/shortcut.md`(각 1회)에 산발적으로 섞여 있는 정도다. **새 글은 평서체로 쓴다.** 기존 문서에 추가할 때만 그 문서의 종결어미를 따라간다.
- "먼저, ~", "다음으로, ~", "마지막으로, ~" 식의 기계적 순서 접속
- "중요한 점은 ~라는 것입니다", "핵심은 ~입니다" 같은 강조 상투구
- "이를 통해 ~할 수 있다", "결론적으로", "종합하면" 같은 마무리 정리 문단
- 글 끝의 "## 정리" / "## 마치며" / "## 결론" 섹션 — **이 위키에는 존재하지 않는다**
- 장식용 이모지 (✨🚀💡). 이모지는 데이터를 나타낼 때만 쓴다
- 모든 문장 길이가 균일한 리듬
- 원문에 없는 내용을 채워 넣어 분량을 늘리는 것

## 1. 세 가지 레지스터

글의 성격에 따라 셋 중 하나를 고른다. 섞지 않는다.

### A. 장문형 — 개념/정책/기준 정리 (2026년 글의 기본값)

대표 예시: `seo/hreflang-canonical.md`, `web/dynamic-range-limit.md`, `seo/seo-cloaking-and-content-gating.md`

- `## 배경` 또는 `## 발견 계기`로 열거나, 소제목 없이 리드 문단 한두 줄로 바로 시작
- 완결된 `~다` 평서문. 주어와 조사를 생략하지 않는다
- 비교·대조가 필요한 지점에만 표를 쓴다
- 맨 아래 `## 참고` 링크 목록

**소제목을 완결된 서술문으로 쓴다.** 이게 2026년 장문형 글의 가장 뚜렷한 특징이다. 명사구로 주제만 던지는 대신 그 섹션의 결론을 소제목에 박아버린다.

- `## canonical은 자기 자신을 가리킨다`
- `## URL과 언어 코드는 단일 출처에서 파생시킨다`
- `## 자동 언어 리다이렉트의 색인 함정`
- `## Google이 비교하는 것과 비교하지 않는 것`
- `## 절대 하면 안 되는 것`

소제목만 훑어도 글의 주장이 읽히는 상태가 목표다. `## 개요`, `## 특징`, `## 사용법` 같은 빈 명사구는 쓰지 않는다.

**발췌 — 소제목 없이 리드 문단으로 시작** (`hreflang-canonical.md`)

> 한 페이지를 여러 언어로 서비스할 때, 검색엔진에 "같은 콘텐츠의 다른 언어 버전"이라는 설정을 제대로 하지 않으면 번역본이 검색엔진 색인에서 잘못될 수 있다.
>
> ## canonical은 자기 자신을 가리킨다
>
> 다국어 페이지의 정규 URL은 각 언어 페이지가 자기 자신을 가리키는 것이 정석이다. ko/en/ja를 하나의 대표 URL로 통합하면 그 한 언어만 색인되고 나머지 번역본은 검색 결과에 노출되지 않는다.
>
> 자기 참조만으로는 부족하다. "이 셋은 같은 콘텐츠의 번역결과"라는 신호를 hreflang으로 따로 줘야 한다.

문단 길이가 들쭉날쭉하다. 두 줄짜리 문단 뒤에 한 줄짜리 문단이 온다. 이 리듬을 살린다.

**발췌 — 발견 계기로 시작** (`dynamic-range-limit.md`)

> ## 발견 계기
>
> velog.io 에서 특정 썸네일만 밝기가 유독 강하게 보여서 확인해보니 HDR 이미지였고, 이걸 제어하는 CSS 속성이 `dynamic-range-limit` 이라는 걸 알게 됨.
>
> > [MDN - dynamic-range-limit](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/dynamic-range-limit)

### B. 메모형 — 팁 나열, 짧은 개념 조각

대표 예시: `monitoring/datadog rum으로 모니터링 할 때 알아두면 좋은것.md`, `monitoring/cardinality-and-dimensionality.md`, `frontend/use-transition-suspense.md`

- 도입부 산문 없이 소제목 + 불릿으로 바로 들어간다
- 불릿을 탭으로 중첩한다. 2~3단계까지 내려간다
- 명사형·체언 종결을 허용한다: `비추`, `잡히지 않음`, `알려줌`, `러스트로 제작되었음`
- 완결 문장과 조각이 한 글 안에 섞여도 된다

**발췌** (`datadog rum으로 모니터링 할 때 알아두면 좋은것.md`)

> - 비용 아끼기
> 	- 세션, 세션 리플레이 줄이기
> 	- datadogLogs로 남기기
> 	- 에러 알람은 logs, rum 둘다 사용가능
>
> - 유저 작성 콘텐츠가 서비스에 있는 경우, 외부 CDN 호출 정보를 대시보드화 하기
> 	- 페이지 Vital에 영향을 끼칠 수 있음.

**발췌 — 불릿 안에 판단을 심는 방식** (`cardinality-and-dimensionality.md`)

> - 데이터를 분석할 때 사용할 수 있는 **속성(키)의 개수**
> - **디멘션을 조합**하면 더욱 세부적인 분석이 가능
> - **즉, 디멘션이 많을수록, 분석할 수 있는 정보가 더 많아짐**
>   - "지난 30분 동안 특정 서비스에서 특정 사용자 ID가 특정 요청을 보냈을 때 발생한 오류"
>     - 시간, 서비스, 환경, 사용자, 요청 Url, 상태 라는 6가지 디멘션을 가지면 위와 같이 분석 가능

### C. 트러블슈팅형 — 겪은 문제와 해결 과정

대표 예시: `library/react-query/fail-request.md`, `error/모노레포에서 서로 다른 react 버전 사용시 에러.md`, `library/biome.md`

- 소제목 골격: `## 현상` → `## 과정` → `## 교훈`, 또는 `## 환경` → 디깅 서사, 또는 `## 도입한 이유` → `## 과정` → `### 비고`
- 1인칭 시간순 서사. 실패한 시도도 지우지 않고 남긴다
- 감정과 감탄을 지우지 않는다

**발췌** (`react-query/fail-request.md`)

> ## 현상
> 최근 몇몇 소수의 유저들에게서 빈 화면이 노출되는 현상이 있었다.
> 한 서비스에서만 발생한게 아니라, 분리되어있는 서로 다른 react, Next.js 애플리케이션에서 발생해서 의아해했다.
>
> ## 과정
> - 아예 요청 자체를 못 보내는 건가?
>   - 디버깅용으로 일반 fetch코드를 심어 놓았다. 잘 요청되는 게 확인됐다.
>
> ## 교훈
> - 동료가 남기는 자료들을 잘 챙겨 보고, 잘 저장해놓자. (거의 1년이된 쓰레드에서 실마리를 발견했다)

**발췌 — 체언 종결 서사** (`모노레포에서 서로 다른 react 버전 사용시 에러.md`)

> B의 package.json에 resolution을 명시해줘도 17버전을 참조함.
> 에러 디깅을 하다가 문득 next.js `transpilePackages` [옵션](https://nextjs.org/docs/app/api-reference/next-config-js/transpilePackages)이 떠오름.

## 2. 레지스터를 관통하는 공통 규칙

### 2-1. 소제목

우선순위는 **서술문 > 구어체 질문 > 명사구** 순이다. 어느 쪽이든 그 섹션이 무슨 얘기를 하는지 소제목만 보고 알 수 있어야 한다.

구어체 질문형은 45개 문서 중 두세 편에만 나오는 소수 패턴이다. **강제하지 않는다.** 자료 성격이 "이게 뭔데?"에 답하는 글일 때만 쓴다.

- `## 이 속성이 뭐 하는 건데?`
- `## 왜 데드코드를 관리해야 하는가?`
- `## 언제 쓰면 좋은가`
- `## 모니터링할 때 자주 보는것들만 나열하자면`

말을 거는 듯한 짧은 명사구도 자주 쓰인다.

- `## 도입한 이유`
- `## 발견 계기`
- `## 지원 현황`
- `## 교훈`
- `## 현상` / `## 과정` / `## 환경`

"~에 대한 이해", "~의 개념", "개요", "소개", "주요 특징" 같은 소제목은 이 위키에 없다.

### 2-2. 1인칭 판단을 살균하지 않는다

원문에 있는 주관적 평가는 중립화하지 않고 그대로 옮긴다. 사용자가 준 자료에 판단이 없으면 억지로 만들지 말고, 있으면 반드시 보존한다.

실제 표현들:

- `2023-10-14 기준 maintanence mode가 되었기 때문에 비추`
- `하나하나 찾아 설정해줘야하는 점이 불편했다.`
- `개발하는 중간중간 정적분석 도구를 사용해 ... 제일 좋다고 생각한다.`
- `그 후 웹스톰을 리로드하면… 겁나 빨라진다.`
- `always로 설정하여 문제를 해결했다...!`
- `eslint가 무거워서 웹스톰이 가끔 매우 느려진다. 온갖 설정을 해줘도..`
- `(~~단순 biome으로 설치하지말 것~~)`

말줄임표 `..`, `…`, 취소선, 느낌표를 쓴다. 정제된 문어체로 다듬지 않는다.

### 2-3. 괄호 방백

본문 흐름을 끊지 않고 옆에서 한마디 덧붙이는 방식을 자주 쓴다.

- `(velog 썸네일이 딱 그 케이스)`
- `(해당 정보를 필터링하는 옵션이 최근 추가됐다.)`
- `(거의 1년이된 쓰레드에서 실마리를 발견했다)`
- `동일한 내용을 가지고 있는 파일들은 ... 1개만 저장한다. ([[Blob]] 형태로)`

### 2-4. 시점을 못 박는다

기술 정보는 언제 기준인지 밝힌다. 시간이 지나 틀려질 정보라는 걸 글 안에 남긴다.

- `2023-10-14 기준 maintanence mode가 되었기 때문에`
- `2026-07 기준 활발히 유지보수되고 있다. (v3.9.1)`
- `현 시점 Chromium 계열 위주.`

### 2-5. 볼드는 아껴 쓴다

한 섹션에 한두 번, 그 섹션의 핵심 명제에만 건다.

- `**Google은 hreflang으로 묶인 URL 집합에 속한 페이지를 정규 URL로 선호한다.**`
- `**전달 방식(HOW) 차이는 OK, 최종 콘텐츠(WHAT) 차이는 NOT OK.**`
- `HDR 이미지/비디오의 **최대 밝기를 어디까지 허용할지** 정하는 CSS 속성.`

문장의 절반을 볼드로 칠하지 않는다.

### 2-6. 출처 표기 세 가지 형식

용도에 따라 골라 쓴다.

1. **맨 아래 `## 참고` 목록** — 링크가 여러 개일 때. em dash로 각 링크가 무엇을 다루는지 한 줄 붙인다

   `- [Localized versions of your pages](https://...) — hreflang 규칙, x-default, 흔한 실수`

2. **소제목 바로 아래 블록쿼트 링크** — 단일 1차 출처일 때

   `> [MDN - dynamic-range-limit](https://developer.mozilla.org/...)`

3. **글 끝 `> 출처:` 한 줄** — 책·강의에서 가져왔을 때

   `> 출처: 데브옵스 엔지니어를 위한 실전 관찰 가능성 엔지니어링`

### 2-7. 코드블록

- 명령어에는 인라인 주석으로 무엇을 하는 건지 붙인다

  `npx fallow audit                      // 변경된 파일만 게이트 (PR 단계 검사)`

- 설정 파일 예시는 실제로 돌아가는 최소 형태로 자른다
- 펜스에 언어 태그를 붙인다: ts, css, bash, json. 에러 로그·출력물은 text

### 2-8. 도구 소개 패턴

여러 도구를 비교할 때 쓰는 고정 형식이다 (`자바스크립트 데드 코드 제거.md`).

```
#### [**도구명**](깃허브_링크)
- 한 줄 특징
- 한 줄 특징
(코드블록)
- 추가 설명

##### 사용후기
- 실제로 써보니 어땠는지
- 아쉬웠던 점
```

### 2-9. 이모지

데이터를 나타낼 때만 쓴다. `seo-cloaking-and-content-gating.md`의 위험도 컬럼이 유일한 사례다.

- `🔴 Critical` / `🟡 Warning` — 표의 위험 수준
- `✅` / `⚠️` / `❌` — 허용/경계/금지 판정

장식으로는 절대 쓰지 않는다.

## 3. Frontmatter

```yaml
---
title: 제목
date: YYYY-MM-DD
updated: YYYY-MM-DD
tags:
  - 태그
---
```

- `title` `date` `updated` `tags` 네 개가 기본형이다
- `created`는 Obsidian이 남긴 흔적이라 있는 글도 있고 없는 글도 있다. **새로 만들 때는 넣지 않는다**
- 기존 문서를 수정할 때 `created`가 이미 있으면 건드리지 않는다
- 날짜는 `2026-07-05` 형태. 기존 문서에 `2026-07-05T15:40:45+09:00` 형태가 있으면 그 형식을 유지한다
- 하이픈이 들어간 태그는 따옴표로 감싼다: `- "react-query"`

### 태그 어휘 (실제 사용 중, 괄호는 사용 횟수)

`javascript`(6) `tip`(5) `정규표현식`(3) `모니터링`(3) `개선`(3) `SEO`(3) `git`(3)
`webstorm`(2) `Web API`(2) `react` `css` `i18n` `디깅` `성능최적화` `"react-query"`
`Sentry` `cloudflare` `플레이어` `단축키` `정규언어` `오브젝트` `my-setting`

**새 태그를 만들기 전에 위 목록에서 먼저 찾는다.** 한글 태그와 영문 태그가 공존하며, 기술명은 소문자 영문, 분류성 태그는 한글인 경향이 있다. 태그는 1~3개.

## 4. 제목 짓기

두 가지 형태가 쓰인다.

- **`주제 - 부연`**: `정규표현식 - 01. 입문 정규표현식`, `관찰 가능성 - 카디널리티와 디멘셔널리티`, `dynamic-range-limit - HDR 이미지/비디오 밝기 제한 CSS 속성`, `git 딥다이브 - git merge, rebase`
- **구어체 서술**: `다국어 페이지 작업시 주의해야할 것 - hreflang / canonical`, `내가 써먹으려고 정리한 단축키 & 명령어 모음`, `eslint에서 biome로`, `react-query 동작 안하는 이슈 해결`

"완벽 가이드", "총정리", "A to Z", "알아보자!" 같은 블로그성 제목은 쓰지 않는다.

## 5. 헤딩 레벨

본문 최상위 헤딩은 `##`가 다수이고, 2026년에 쓴 글은 전부 `##`로 시작한다. **새 글은 `##`로 시작한다.**

기존 문서에 추가할 때는 그 문서가 `#`으로 시작하면 `#`을, `##`면 `##`을 따른다. 한 문서 안에서 레벨을 섞지 않는다.

## 6. 내부 링크

Obsidian wiki 링크를 쓴다. gatsby-theme-primer-wiki가 `[[WikiLink]]`를 지원한다.

- 문서 참조: `[[Blob]]` — 확장자 없이 파일명만
- 특정 섹션 참조: `[[regex_01#DFA형 키워드 결정성과 비결정성]]`
- 이미지: `![[git-hash-tree.png]]`
- 외부 링크는 일반 마크다운: `[텍스트](https://...)`

본문 흐름 안에 자연스럽게 끼워 넣는다. "관련 문서" 섹션을 따로 만들어 링크를 몰아넣는 방식은 이 위키에 없다.

## 7. 작성 후 자가 점검

글을 쓴 뒤 아래를 확인한다. 하나라도 걸리면 고친다.

- [ ] "~할 수 있습니다" 경어체가 섞여 있지 않은가 (경어체 기존 문서를 수정하는 경우가 아닌 한)
- [ ] "먼저 / 다음으로 / 마지막으로" 기계적 접속이 있는가
- [ ] `## 정리` `## 결론` `## 마치며` 섹션을 만들었는가 → 지운다
- [ ] 모든 문단 길이가 비슷한가 → 리듬을 깬다
- [ ] 원문에 없던 설명을 상상해서 채웠는가 → 지운다
- [ ] 원문에 있던 주관적 판단(비추, 불편했다, 겁나 빨라진다)을 중립화했는가 → 되돌린다
- [ ] 장식용 이모지가 있는가 → 지운다
- [ ] 소제목이 `개요` `특징` `사용법` 같은 빈 명사구인가 → 결론을 담은 서술문으로 바꾼다
- [ ] 시간이 지나면 틀려질 정보에 시점(`2026-08 기준`)을 붙였는가
- [ ] 출처 링크가 있는가
- [ ] 도입부에 "왜 이걸 찾아봤는지"가 있는가 (순수 레퍼런스 문서가 아니라면) → 없으면 사용자에게 묻는다
- [ ] 그 계기를 사용자가 말한 표현 그대로 썼는가, 아니면 매끄럽게 다듬어버렸는가
