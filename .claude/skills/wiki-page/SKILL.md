# r0k Wiki 페이지 작성기

`content/` 아래 마크다운 문서를 만들거나 갱신한다.
**핵심 가치는 "말투 재현"이다.** 정보를 옮기는 것만으로는 실패다. 사용자가 나중에 읽었을 때 자기가 쓴 글로 느껴져야 한다.

## 언어: 모든 출력은 한국어

---

## Step 0. 말투 레퍼런스를 먼저 읽는다 (건너뛰지 않는다)

본문을 한 글자라도 쓰기 전에 **반드시** `.claude/skills/wiki-page/references/voice.md`를 읽는다.
세 가지 레지스터, 소제목 짓는 법, 1인칭 판단 보존 규칙, frontmatter 형식, 금지 표현이 전부 거기 있다.

기억에 의존하지 않는다. 매번 읽는다.

---

## Step 1. 입력 수집

사용자가 주는 입력은 세 형태 중 하나다.

### 1-A. 텍스트를 직접 준 경우

그대로 재료로 쓴다. 사용자가 쓴 표현·판단·감탄은 **원문 그대로 살릴 후보**로 표시해둔다.

### 1-B. URL을 준 경우

`obsidian:defuddle` 스킬로 본문을 추출한다. WebFetch보다 토큰 효율이 좋고 네비게이션 잡음이 제거된다.

- 단, `.md`로 끝나는 URL은 이미 마크다운이므로 WebFetch를 바로 쓴다
- defuddle이 실패하면 WebFetch로 폴백한다
- 추출한 뒤 **원문 URL을 반드시 기록**해둔다. `## 참고`에 들어가야 한다

### 1-C. 텍스트 + URL 둘 다

사용자가 쓴 텍스트가 주(主), 링크 내용이 보조다. 사용자의 문장과 판단을 우선 배치하고 링크에서 가져온 사실로 보강한다.

### 1-D. 계기를 확보한다 (자료만으로는 절대 안 나오는 부분)

이 위키에서 가장 잘 읽히는 글들은 **"내가 왜 이걸 알아보게 됐는지"로 시작한다.** 실제 도입부 소제목들이다.

- `## 발견 계기` — velog 썸네일이 유독 밝아서 (`dynamic-range-limit.md`)
- `## 도입한 이유` — eslint가 무거워서 웹스톰이 느려져서 (`biome.md`)
- `## 배경` — 봇 전용 경량 서버를 고려하다가 (`seo-cloaking-and-content-gating.md`)
- `## 현상` — 소수 유저에게 빈 화면이 떠서 (`react-query/fail-request.md`)
- `## 환경` — 모노레포에서 react 버전이 갈려서 (`모노레포에서...에러.md`)
- `## 왜 데드코드를 관리해야 하는가?` (`자바스크립트 데드 코드 제거.md`)

MDN 문서나 블로그 글을 그대로 옮기면 이 부분이 통째로 비고, 그 순간 남의 글이 된다.

**그래서 자료에 계기가 없으면 사용자에게 묻는다.**

```
이거 어쩌다 찾아보게 되셨어요? (한 줄이면 충분합니다)
- 실무에서 겪은 문제 / 그냥 발견 / 도입 검토 중 / 없으면 생략
```

- 답을 주면 그 표현을 거의 그대로 살려 도입부로 쓴다. 다듬어서 매끄럽게 만들지 않는다
- "없다"고 하거나 순수 레퍼런스성 문서(`Web_API/Blob.md` 같은)면 계기 없이 바로 본론으로 들어간다
- **계기를 지어내지 않는다.** 없으면 없는 대로 둔다

### 수집 시 하지 말 것

- 원문에 없는 내용을 지식으로 채워 넣어 분량을 늘리는 것
- 원문의 주관적 평가("이건 좀 별로", "이게 제일 낫다")를 중립 서술로 바꾸는 것
- 링크 본문을 통째로 번역·전재하는 것 (위키는 요약·판단의 공간이지 아카이브가 아니다)

## Step 2. 기존 문서 검색 → 신규인가 추가인가

**새 파일을 만들기 전에 반드시 검색한다.** 이 위키는 문서 수가 적어서(50개 미만) 전수 확인이 가능하다.

검색은 **저장소 루트 절대경로 기준**으로 돌린다. cwd가 하위 디렉토리로 내려가 있으면 상대경로 `content`는 매치 없이 빈 결과를 뱉는데, 이건 에러가 아니라 경고라서 "관련 문서 없음"으로 오판하고 중복 문서를 만들게 된다.

```bash
WIKI=/Users/yuroklee/code/padawanr0k/wiki   # cwd가 어디든 이 경로를 쓴다

# 경로 sanity check — 40 미만이면 경로가 틀린 것이므로 중단하고 경로부터 고친다
find "$WIKI/content" -name '*.md' | wc -l

# 파일명 훑기 (공백 포함 파일명 주의 — for 루프 word splitting 금지)
find "$WIKI/content" -name '*.md' | sort

# 주제 키워드로 본문 검색
grep -rn "키워드" "$WIKI/content" --include='*.md'
```

**결과가 0건이면 검색이 실패한 것부터 의심한다.** 파일 개수 확인이 40 이상으로 나온 뒤의 0건만 진짜 0건이다.

검색 결과를 세 갈래로 판정한다.

| 판정 | 조건 | 처리 |
| --- | --- | --- |
| **추가** | 같은 주제를 다루는 문서가 이미 있다 | Step 3-B로 간다 |
| **신규 + 연결** | 주제는 다르지만 교차하는 문서가 있다 | Step 3-A로 가되 `[[링크]]`로 잇는다 |
| **신규** | 관련 문서 없음 | Step 3-A |

**"추가"로 기울 때가 많다.** 도구 하나, 속성 하나를 위해 새 파일을 만들기보다 기존 문서에 섹션으로 붙이는 편이 이 위키의 관성에 맞다.
예: `fallow` 도구는 새 파일이 아니라 `자바스크립트 데드 코드 제거.md`에 `#### fallow` 섹션으로 들어갔다.

판정이 애매하면 진행 전에 사용자에게 묻는다.

### 파일명

- kebab-case 영문이 기본: `hreflang-canonical.md`, `dynamic-range-limit.md`
- 한글이 자연스러우면 한글 파일명도 쓴다: `자바스크립트 데드 코드 제거.md` (공백 포함 가능)
- 시리즈는 숫자 접미사: `regex_01.md`, `git-deep-dive-01.md`

### Frontmatter

```yaml
---
title: 제목
date: 오늘 날짜
updated: 오늘 날짜
tags:
  - 태그
---
```

`created`는 새 글에 넣지 않는다. 태그는 voice.md의 기존 어휘에서 먼저 고른다.

### 본문

`.claude/skills/wiki-page/references/voice.md`의 레지스터 A/B/C 중 하나를 골라 그 형식으로 쓴다. 헤딩은 `##`부터 시작한다.

## Step 3-B. 기존 페이지에 추가

`fe63fe7`(데드 코드 제거 위키에 fallow 도구 추가) 커밋이 정답 사례다. 그 방식을 따른다.

### 규칙

1. **`updated`만 갱신한다.** `date`와 `created`는 손대지 않는다
   ```
   date: 2023-10-14        ← 그대로
   created: 2023-10-14...  ← 그대로
   updated: 2026-07-27     ← 오늘 날짜로 교체
   ```

2. **형제 섹션의 형태를 복사한다.** 새 섹션은 옆 섹션과 헤딩 깊이·내부 구조가 같아야 한다
   - 형제가 `#### [**도구**](링크)` + 불릿 + `##### 사용후기` 구조면 똑같이 만든다
   - 형제가 문단형이면 문단형으로 쓴다

3. **파일 끝이 아니라 논리적 위치에 끼워 넣는다.** fallow는 knip 다음, "이외 도구들" 앞에 들어갔다. 기존 문서의 흐름을 읽고 자리를 정한다

4. **기존 문서의 말투를 따른다.** 그 문서가 경어체면 경어체로, 체언 종결이면 체언 종결로 쓴다. 새 섹션만 문체가 튀면 안 된다

5. **태그를 갱신할지 판단한다.** 추가한 내용이 새로운 분류를 만들면 태그를 하나 더한다. 아니면 그대로 둔다

---

## Step 4. 백링크 연결

Step 2에서 찾은 관련 문서가 있으면 잇는다.

- **새 문서에서 참조**: 본문 흐름 안에 `[[문서명]]`을 자연스럽게 끼워 넣는다
  예: `동일한 내용을 가지고 있는 파일들은 ... 1개만 저장한다. ([[Blob]] 형태로)`
- **기존 문서에서 참조**: 관련 있는 문장 옆에 링크를 건다

"관련 문서" 섹션을 새로 만들어 링크를 몰아넣지 않는다. 이 위키에 그런 패턴은 없다.

기존 문서를 건드리는 것이므로 **연결 전에 사용자에게 확인**한다.

---

## Step 5. 자가 점검

`.claude/skills/wiki-page/references/voice.md`의 "7. 작성 후 자가 점검" 체크리스트를 실행한다. 특히:

- `## 정리` / `## 결론` / `## 마치며` 를 만들었으면 지운다
- "먼저 / 다음으로 / 마지막으로" 기계적 접속을 지운다
- 원문의 주관적 판단을 중립화했으면 되돌린다
- 소제목이 `개요` `특징` `사용법` 같은 빈 명사구면 결론을 담은 서술문으로 바꾼다 (구어체 질문형은 소수 패턴이라 강제하지 않는다)
- 시간이 지나면 틀려질 정보에 시점을 붙인다

## 출력 형식

### 작성 전 보고

```
경로: content/posts/web/dynamic-range-limit.md  (신규)
제목: dynamic-range-limit - HDR 이미지/비디오 밝기 제한 CSS 속성
태그: css
레지스터: A(장문형) — 개념 정리 글이라

검색 결과:
  관련 없음

이대로 쓸까요?
```

기존 문서에 추가하는 경우:

```
대상: content/posts/javascript/자바스크립트 데드 코드 제거.md  (추가)
위치: "#### knip" 다음, "#### 이외 도구들" 앞
형식: 형제 섹션과 동일한 #### [**도구명**](링크) + 불릿 + ##### 사용후기
frontmatter: updated만 2026-08-23으로 갱신
```

### 작성 후

파일 경로와 함께 백링크 제안이 있으면 함께 보고한다. 커밋은 사용자가 요청할 때만 한다.

## 커밋 메시지 (사용자가 커밋을 요청한 경우)

이 저장소의 커밋 메시지는 짧은 한국어 명사구다.

```
카디널리티, 디멘셔널리티
hreflang-canonical추가
dynamic-range-limit CSS 속성 위키 추가
데드 코드 제거 위키에 fallow 도구 추가
```

`feat:` 같은 prefix는 최근 커밋에서 쓰지 않는다.
